*Date:* 2026-08-14
*Status:* accepted
*Amends:* CLAUDE.md §3's dependency table ("Long lists → Paging 3"), `docs/UI.adoc` §B14.3

== The rule this deviates from

CLAUDE.md §3 names *Paging 3* as the mandated library for long lists, and §5 repeats it: _"Page or
lazily load the episode list (Paging 3 or a `Flow` of a limited query). Do not load 5,000 rows into
memory to render 20."_ `docs/UI.adoc` §B14.3 hedged, allowing "paging or a keyed ``LazyColumn``", and
`docs/backlog.adoc` carried the open question with one instruction attached: *measure before adding
the dependency.*

== What was measured

`EpisodeListScaleTest` (`:core:database`) seeds a feed and times the first emission of
`EpisodeListRepository.observeEpisodes` -- the query the screen actually binds to, through the real
Room DAO and the real entity→domain mapping, with realistic show-notes-sized `description` columns.

|===
| Rows | Filter | First emission

| 500
| `All`
| *6 ms*

| 9,500
| `All`
| *82 ms*

| 9,500
| `To decide`
| *132 ms*
|===

500 is the size `docs/UI.adoc` §B14.3 names. 9,500 is what the author's own four subscriptions hold on
the real device (README), i.e. the whole library at once -- which no screen actually asks for, since
S2 is per-podcast.

`To decide` is the slowest because of its `+NOT IN (SELECT ... FROM episode_ledger)+` sub-select, and
it is also the default view, so it is the number that matters most. It is still an eighth of a
second for every episode the author owns.

These are JVM numbers against in-memory SQLite. A phone's storage is slower -- call it a few times
that, so a few hundred milliseconds, *once, at screen open*, for a query no screen actually issues
at that size.

== The decision

*Do not add Paging 3.* The keyed `LazyColumn` `docs/UI.adoc` §B14.3 already permits stays, and that
document now says so definitely rather than offering a choice.

The reasoning, in the order it matters:

. *The problem the dependency solves does not exist at this scale.* CLAUDE.md's own anti-pattern
list says not to add a library for something already handled well, and its instruction to measure
first is what produced this table.
. *`LazyColumn` already does the part that matters.* "Do not load 5,000 rows into memory to render
20" is about _rendering_, and a keyed `LazyColumn` composes only what is visible. What the list
holds is a `List` of small data objects -- titles and descriptions the DB has already read.
. *Paging is not free.* It replaces one `Flow<List<T>>` with a `PagingSource`, a `PagingData`
flow, a Compose paging artifact and a placeholder story, in every screen that shows episodes --
and the counts, the bulk-selection scope and the "undecided" predicate all read the same query
today. That is a lot of moving parts to make a 132 ms query into a 20 ms one nobody was waiting
on.

== What would reopen it

The measurement is committed as a test with deliberately generous budgets, so it fails on a change
in the _shape_ of the query rather than on a busy CI runner. Reopen this if:

* a screen ever needs the whole library rather than one podcast's episodes, at an order of magnitude
more rows than today; or
* the `To decide` sub-select grows a join, or the filter gains a clause that stops using the index --
the scale test is the thing that would notice; or
* profiling *on a device* shows the first frame of S2 waiting on the query. That has not been
measured, and it is the one part of this decision that JVM numbers cannot settle.

== Consequences

* `docs/UI.adoc` §B14.3 now states the keyed `LazyColumn` as the requirement, not one of two options.
* CLAUDE.md §3's table entry is superseded for this list specifically. It stands as a general
preference; nothing else in the app renders a long list.
* No new dependency, and `gradle/libs.versions.toml` gains nothing.
